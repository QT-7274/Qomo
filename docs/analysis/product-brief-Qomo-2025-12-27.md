# Product Brief: Qomo

**Date:** 2025-12-27
**Author:** drogbaqu

---

## Executive Summary

Qomo 是一个面向高频使用对话式 AI 的用户的可视化 Prompt 资产库与组装工具。它将 Prompt 从“每次重写的文本”升级为“可复用的资产”：用户可以把常用 Prompt 拆分为模块（如角色、目标、约束、输出格式、检查清单等），也可以维护为带变量的模板。在每次提问前，用户通过“模块化拼装 + 变量填充 + 约束包选择”，生成一份结构清晰、约束明确、可直接使用的最终 Prompt，并一键复制/导出给用户选择的外部 AI（一期不做模型直连）。未来，Qomo 支持导入/导出与社区分享，形成可迁移、可协作迭代的 Prompt 资产库。

## Core Vision

### Problem Statement

对话式 AI 的提问质量高度依赖 Prompt 的结构与约束，但高频用户在每次提问前都要重复编写或临时拼凑 Prompt（角色、目标、边界、输出格式、背景信息等）。这个过程繁琐、容易遗漏关键约束，导致提问准备成本高、输出质量不稳定、优质 Prompt 难以沉淀复用与迭代。

### Primary Users & Core Use Cases（核心用户与场景）

- 希望提升工作效率的工作者：日常要写方案、总结、邮件、汇报、PRD、脚本说明等，反复向对话式 AI 提问，但每次从零组织 Prompt 很耗时。
- 重度与 AI 交互的使用者：需要在重复性工作场景/工作任务中持续复用 Prompt，追求“少返工、输出更稳定”。

### User Segments（用户分层）

- 新手用户：更倾向“单次 Prompt 直接用”，需要最短路径（选模板 → 填 1-2 个变量 → 一键导出），以及导出前的轻量提醒（占位符未填/输出格式提示）。
- 高阶 Prompt 工程用户：更倾向“多次复用 + 组装”，需要模块化资产、变量体系、组合预览与可维护性（如标签/版本/导入导出）。

### Primary vs Secondary Users（主用户与次用户）

- 主用户：一期主要聚焦上述两类（新手与高阶）的个人使用者。
- 次用户：一期暂不区分（团队协作/社区分享者作为后续扩展方向）。

### Problem Impact

- 重复劳动：相似问题反复从零组织 Prompt，提问前成本高。
- 质量波动：约束/格式/边界遗漏 → 多轮纠错与返工。
- 资产不可管理：优质 Prompt 分散在聊天记录、笔记、剪贴板，缺乏结构与版本。
- 难以迁移协作：个人模板难导出；团队最佳实践难共享、难迭代。

### Why Existing Solutions Fall Short

- 通用笔记/文档/剪贴板：能存放但难以“结构化资产化”，缺少模块化复用、变量填充、组合预览与导出前校验。
- Prompt 展示/检索型库：偏“发现与收藏”，但不覆盖“按我的工作流组装生成一份可直接使用的最终 Prompt”。
- 纯文本模板：维护成本高、结构不可见、组合与版本演进困难；很难把“有效约束”沉淀为可复用组件。

### Proposed Solution

Qomo 提供一个以“Prompt 资产化 + 生成工作流”为核心的工作台：

1) Prompt 资产模型（可视化管理）
- 模块（Module）：可复用片段（如 Role / Goals / Constraints / Output Format / Examples / Safety），支持标签、搜索、复用。
- 模板（Template）：由多个模块组成，并包含变量槽位（Variables），用于快速定制与复用。
- 约束包（Constraint Packs）：将常见有效约束产品化为可组合选项，按场景选择：
  - 输出约束：要求结构/格式（如 Markdown 小标题、表格、JSON Schema）。
  - 边界约束：定义范围与禁止项（如“不确定先提问”“不要编造”“只使用给定上下文”）。
  - 质量约束：引导更可靠流程（如“先列假设与缺失信息”“输出前自检清单”）。

2) 生成工作流（面向提问前一公里）
- 选择模板/模块 → 填变量（本次问题/上下文/偏好）→ 勾选约束包 → 生成最终 Prompt（结构化预览）。
- 一期交付：复制/导出文本（不直连模型，平台无关）。

3) 轻量校验（Preview/Lightweight Check）
- 导出前做最小但高价值的检查：占位符未填、关键约束缺失提示、疑似敏感信息提示/遮罩建议、输出结构约束提醒（如需 JSON/表格时）。

4) 可迁移与可演进
- 导入/导出模板与模块（便于迁移、备份、团队共用）。
- 后续：社区分享与迭代（评分/版本/衍生），形成“可组合的 Prompt 资产网络”。

### Safety & Trust Boundaries（安全与信任边界）

由于 Prompt 可能包含敏感信息（个人隐私、公司机密、账号密钥等），Qomo 将把“安全与可控”作为核心体验的一部分：

- 一期不直连模型：只生成并导出文本，降低数据外流与平台锁定风险。
- 资产与单次问题分离：模板/模块作为可维护资产；单次问题默认不沉淀或可控沉淀，降低敏感内容长期存储风险。
- 非阻断式安全提示：导出前轻提示敏感信息并提供一键遮罩，同时允许用户继续导出。
- 导入可信机制（面向未来社区）：展示来源/版本/变更，并对潜在“隐藏指令/高风险语句”进行提示，避免资产被污染。

### Key Differentiators

- Qomo 同时提供 Prompt 资产库（收藏/管理）与生成工作流（组装→预览/轻量校验→导出），让 Prompt 成为可控、可复用、可迁移的生产资料。
- 约束包机制：把“有效约束”产品化为可选组件，按场景选择与复用，降低学习与试错成本。
- 轻主路径优先：为新手与高频提问提供“选模板→填变量→一键生成并复制”的最短路径，高级选项折叠；同时为高阶用户提供模块化拼装能力。
- 一期清晰边界：只做复制/导出，把生成工作流与资产模型先打扎实；未来再扩展社区与生态。

## Success Metrics

### North Star Metric（北极星指标）

- **WAEP（Weekly Active Exporters with Reuse）**：每周至少有一次“生成并导出/复制”，且当次会话包含“复用”（模块/模板/历史组合任一）并**实际参与生成**。
  - 目的：把“产出价值 + 复用减少返工”绑定在一起，避免只追 DAU/导出次数等虚荣指标。

### Activation（两段式激活）

- **Activation-1（首次价值）**：首次会话完成 `生成 → 导出/复制`。
- **Activation-2（复用价值）**：后续会话完成 `复用（模块/模板/历史组合并实际参与生成）→ 生成 → 导出/复制`。

### User Success Metrics（用户成功）

- **更快产出高质量 Prompt**
  - 指标：核心路径完成率（进入 → 生成 → 导出/复制）、完成用时分布（如 p50/p95）。
- **复用资产减少返工**
  - 指标：复用会话占比、复用次数/人、复用资产覆盖（模块/模板/历史组合）。
- **Aha 时刻达成（随取随用、随时组装）**
  - 指标：首次达成 Aha 行为占比（示例：创建≥1模块 + 生成≥1次 + 导出≥1次）。

### Business Objectives（业务目标）

- **拉新**：新用户增长、渠道转化（如分享/邀请带来的新增）。
- **留存**：次日/7日/30日留存（按“有效活跃”口径）。
- **活跃**：DAU/WAU/MAU、人均生成/导出/复用次数。
- **口碑传播**：分享/邀请行为与回流（优先用可归因链路的数据）。

### Key Performance Indicators（关键 KPI）

- **核心漏斗**：进入工作台 → 选择模板/组合模块 → 生成 → 导出/复制 转化率。
- **复用效率**：复用会话占比、复用资产占比（只统计“实际参与生成”的复用）。
- **产出强度**：人均导出/复制次数、人均生成次数。
- **粘性与留存**：DAU/WAU、次日/7日/30日留存。

### Quality Gates（质量门槛：前端 + 云函数/边缘函数 + KV）

> 质量门槛优先：当核心链路失败率或 p95/p99 延迟显著恶化时，增长类指标不作为成功判断依据。

- **核心链路失败率**：生成/导出/复制的 `success=false` 占比（按版本/环境/地区拆分）。
- **函数调用可用性**：错误率（超时/限流/5xx）+ p95/p99 延迟。
- **KV 读写可用性**：读写错误率 + 重试/冲突（如存在）。
- **前端稳定性与性能**：JS 错误/白屏、关键交互耗时（如“点击生成→预览可用”的 p95）。

### Valid Export（有效导出，N = 5 分钟）

- **定义**：导出后 5 分钟内是否出现频繁“再次生成/再次导出/反复编辑”。
- **目的**：作为“少返工”的代理指标，衡量导出是否足够可用。

## MVP Scope

### Core Features

- **价值主线（复用优先）**
  - 把 Prompt 变成可复用资产：随取随用、随时组装、一键导出
  - 核心目标：通过模块/模板/历史组合的复用，减少重复劳动与返工

- **Prompt 资产化管理（必须）**
  - 模块（Module）：创建/编辑/删除、标签、搜索、复用
  - 模板（Template）：由多个模块组成，支持变量槽位，用于快速定制与复用
  - 约束包（Constraint Packs）：MVP 仅提供少量内置约束包（克制范围，避免膨胀为第二套模板系统）

- **生成工作流（必须）**
  - 选择模板/模块 → 填变量 → 选择约束包 → 生成最终 Prompt（结构化预览）
  - 支持“复用上次组合/最近组合”（快速进入状态）

- **导出与使用（必须）**
  - 一键复制/导出文本（一期不做模型直连）

- **导出前轻量校验（G，MVP 必做）**
  - 占位符未填提醒（高亮变量 + 导出前提示，默认非阻断）
  - 输出格式约束提醒（如选择 JSON/表格等时给出一致性提示，非阻断）
  - 空内容/全占位符阻断导出（唯一硬拦截）
  - 敏感信息提示/遮罩建议（非阻断）
  - 原则：除“空内容/全占位符”外，其余校验均为非阻断提示

- **新手也能达成 Aha（必须）**
  - 新手首次体验目标路径：创建 1 个模块 → 用模板生成 → 复制导出

> 说明：由于 Top 1 具体业务场景尚未选定，MVP 先交付“跨场景通用链路”，
通过模板/模块/复用来覆盖写方案、总结、邮件、汇报、PRD、脚本说明等多类输出。

### Out of Scope for MVP

- 社区/市场能力：分享、评分、衍生（不做）
- 团队协作与权限系统（不做）
- 复杂版本管理：分支、对比、回滚等（不做）

### MVP Success Criteria

- **核心判断：用户使用率/使用频次提升**
  - 优先关注活跃（DAU/WAU）、留存（次日/7日/30日）
- **价值兑现：从首次价值到复用价值**
  - Activation-1（首次生成→导出/复制）稳定达成
  - Activation-2（复用参与生成→导出/复制）出现明显增长趋势
- **质量门槛稳定（前端 + 云函数/边缘函数 + KV）**
  - 核心链路失败率与 p95/p99 延迟保持可控

### Future Vision

- **团队共享 Prompt 资产网络**
  - 团队沉淀模块、模板、约束包，形成可治理、可迁移的知识资产
- **市场/社区生态**
  - 模板与模块的发布、评分、衍生与版本演进，形成“可组合的 Prompt 资产网络”

## 附录：下一轮 BMAD 头脑风暴输入与边界（2026-03-06）

> 用途：为下一波“执行 BMAD 头脑风暴工作流”提供统一问题陈述、探索维度、边界约束与发散顺序，避免讨论过早收敛或遗漏关键范围。

### 1. 脑暴问题陈述（统一起点）

我们要探索的不是“再做一个普通 Prompt 编辑器”，而是：

- 能否定义一个**既兼容网页版、也能作为 VS Code 插件同步开发的产品形态**；
- 该产品延续 Qomo 的核心价值，但从“Prompt 模板/模块管理”进一步升级为“**可复用能力编排的 Prompt 工作台**”；
- 用户可以构建**带插槽（slots）的 Prompt**，并在插槽中装配子 agent、skills、MCP、工具调用、上下文片段、约束块等能力；
- 用户的核心收益是：在 IDE 等高频任务场景里，**复用已经配置好的 Prompt + 能力组合**，减少每次任务前重复交代背景、规则、工具和执行方式；
- 同时要评估：这是否应被视为 **Qomo 的自然演进 / 重构方向 / 并行孵化的新产品形态**。

可用作下一轮脑暴总问题：

- “如果 Qomo 要从 Prompt 资产库演进为可跨 Web 与 VS Code 复用的能力化 Prompt 工作台，它最合理的产品定义、核心场景、能力结构、技术路线与重构路径分别是什么？”

### 2. 必须覆盖的探索维度

#### 2.1 产品定位

- 它到底是 Prompt Builder、Agent Workflow Builder、IDE Copilot Layer，还是“可复用 AI 工作单元编排器”？
- 核心价值主张是什么：省重复描述、提升结果稳定性、复用团队最佳实践，还是统一 Web/IDE 两端体验？
- 面向个人高频用户优先，还是天然要为小团队协作做准备？
- 与 Qomo 当前定位的连续性在哪里，跃迁点又在哪里？

#### 2.2 用户场景

- 哪些场景最值得优先支持：编码任务启动、代码审查、需求分析、调试排障、文档生成、跨角色协作？
- 用户在 Web 端和 IDE 端分别会在什么时刻使用它？
- “复用已配置 Prompt”真正发生在任务的哪个节点：任务开始前、任务进行中、结果复查时，还是团队交接时？
- 哪类场景必须依赖 IDE 上下文，哪类场景更适合在 Web 中策划和管理？

#### 2.3 功能结构

- 插槽化 Prompt 的最小对象模型是什么：Prompt、Slot、Capability、Agent、Skill、MCP、Tool Call、Context Block、Guardrail？
- 插槽是静态占位，还是带类型、约束、可选项、默认值、执行时机的能力接口？
- 用户如何创建、配置、组合、预览、执行、保存与分享这些资产？
- 运行时是否只是“生成可发送的 Prompt”，还是会进一步触发工具/agent/MCP 编排？
- 是否需要区分“设计时资产”和“运行时实例”？

#### 2.4 技术 / 插件可行性

- Web 与 VS Code 插件能否共享同一套领域模型、配置协议和渲染/编排核心？
- 哪些能力必须在插件侧完成（IDE 上下文、命令、文件选择、编辑器交互），哪些能力适合保留在 Web 端？
- MCP、工具调用、子 agent 装配在插件环境中的安全边界与权限模型怎么定义？
- 同步策略是本地优先 + 云端同步，还是导入导出优先？
- 如果先做插件，是否会反向限制 Web 端产品形态；如果先做 Web，又是否会导致 IDE 集成变成补丁式能力？

#### 2.5 Qomo 重构路线

- 是在现有 Qomo 上渐进重构，还是抽出新的核心引擎，再让 Web/插件双端复用？
- 哪些现有概念可以直接继承：模板、模块、变量、约束包、导入导出？
- 哪些概念需要升级或替换：模板 → 能力化 Prompt、模块 → 可执行 capability、变量 → typed slots？
- 是否需要经历“Qomo 1.x 资产管理 → Qomo 2.x 能力编排”的过渡带？
- 数据迁移、用户心智迁移、UI 架构迁移的成本各是什么？

### 3. 边界 / 非目标（本轮脑暴先不解决）

- **不开始编码，不做原型实现，不做技术 Spike。**
- **不在本轮直接锁定最终产品方案。** 本轮目标是把问题空间与选项空间摊开。
- **不把讨论扩散成“所有 IDE/所有宿主平台”**；插件可行性先以 VS Code 为主。
- **不深入商业化、定价、增长渠道等经营议题**，除非它直接影响产品定位判断。
- **不提前承诺复杂团队协作、权限系统、市场/社区生态**，这些最多作为后续方向记录。
- **不在本轮定义完整底层协议或所有插件 API 细节**；这里只判断哪些技术约束会改变产品设计。
- **不默认产品一定要从“Prompt 文本生成”直接跃迁到“全自动 Agent 执行平台”**；需要把“生成型”与“执行型”作为不同方案比较。

### 4. 建议的发散顺序（避免一上来陷入实现细节）

1. **先定“为什么值得做”**
   - 明确用户到底在重复交代什么，当前 Qomo 为什么还不够。
2. **再定“谁最痛、什么时候最痛”**
   - 聚焦优先用户与高频场景，避免空泛讨论。
3. **再发散“它究竟是什么产品”**
   - 产出 2-4 种候选定位，而不是过早认定唯一答案。
4. **再拆“核心对象模型与功能结构”**
   - 明确 slot / capability / prompt / context / execution 的关系。
5. **再评估 Web + VS Code 的技术与插件边界**
   - 看哪些产品想法在双端成立，哪些会被宿主限制。
6. **最后讨论 Qomo 重构路线**
   - 评估渐进演进、双轨孵化、核心引擎先行等路线。
7. **收敛为下一步决策清单**
   - 明确需要继续验证的假设、关键分歧、建议产出物。

### 5. 下一轮脑暴建议产出物

- 1 份清晰的产品机会陈述

## 附录：BMAD 头脑风暴纪要（2026-03-06）

> 性质说明：以下内容属于 **Qomo 的未来演进探索**，用于摊开问题空间与选项空间，**不替代** 当前已经存在的 MVP / PRD / UX / Architecture 基线，也不在本轮锁定唯一最终方案。

### 1. 开场问题陈述

如果 Qomo 不再只停留在“Prompt 资产库”，而是进一步演进为一个 **可跨 Web 与 VS Code 复用的、带插槽的 Prompt 工作台**，那么它究竟应该被定义成什么产品？

这里的关键不是“让 Prompt 更好编辑”，而是：

- 让用户把一次次重复交代的内容（角色、背景、约束、工具、上下文、执行方式）沉淀为可复用的工作单元；
- 让这些工作单元既能在 Web 中被设计、整理、管理，也能在 VS Code 中被直接调用；
- 让 Qomo 从“管理 Prompt 资产”升级到“管理可复用 AI 工作方式”。

一句话概括本轮脑暴主题：

- **我们要探索的，是 Qomo 是否能演进为一个面向高频 AI 用户的“能力化 Prompt 工作台”，而不是另一个 Prompt 编辑器。**

### 2. 第一轮发散：为什么这件事值得做

#### 2.1 用户真正反复在“重复交代”的是什么

- 不是只有 Prompt 文本本身，而是整套任务启动条件：
  - 我要你扮演什么角色；
  - 用什么输入上下文；
  - 遵守哪些边界与输出格式；
  - 可以调什么工具 / MCP / 子 agent；
  - 如何开始、如何复查、如何交付。
- 当前很多高频用户的真实工作方式，已经从“写一句 Prompt”变成“反复重建一套任务启动脚手架”。

#### 2.2 Qomo 当前形态为什么还不够

- 当前 Qomo 更擅长管理“Prompt 资产”，但还没有把“能力装配”作为一等对象。
- 模板 / 模块 / 变量可以覆盖一部分复用，但对 IDE 场景下的上下文、工具、执行约束承载不足。
- 当用户进入编码、调试、评审等高频工作流时，真正想复用的是“一个任务包”，而不是一段独立文本。

#### 2.3 值得做的根本原因

- 从“减少重复描述”升级到“减少重复启动工作流”。
- 从“提升单次输出质量”升级到“提升跨任务稳定性与可迁移性”。
- 从“个人 Prompt 收藏夹”升级到“个人 / 小团队最佳实践容器”。

### 3. 第二轮发散：谁最痛、什么时候最痛

#### 3.1 优先用户画像

- **高频 IDE 用户**：开发者、技术 PM、AI 协作型工程师，在编码、调试、重构、评审时频繁调用 AI。
- **高频知识工作者**：在 Web 端整理模板、约束、输出规范，但也希望在 IDE 中复用同一套工作方法。
- **个人先行的小团队核心成员**：还不需要复杂协作系统，但已经开始形成“团队默认做法”。

#### 3.2 高价值场景地图

- **任务开始前**：快速加载一个“任务启动包”，避免每次重新描述目标、边界、输入与方法。
- **任务进行中**：根据当前上下文补充代码片段、文件范围、历史约束、复查规则。
- **结果复查时**：套用审查模板、检查清单、回归验证框架。
- **团队交接时**：把“怎么做这类任务”沉淀成可共享资产，而不是口头传递。

#### 3.3 Web 与 IDE 的天然分工

- **Web 更适合**：策划、设计、整理、分类、沉淀、比较、版本化。
- **IDE 更适合**：绑定当前代码上下文、选择文件、触发任务、快速复用、边做边调用。
- 因此产品不是“Web 或 插件二选一”，而更像是“同一套资产在两个宿主上的不同工作面”。

### 4. 第三轮发散：它究竟可能是什么产品

本轮不收敛为唯一答案，而是保留 4 个有区分度的候选方向。

#### 方向 A：结构化 Prompt 资产工作台

- **定义**：核心仍是 Prompt Builder，但升级为带 typed slots 的结构化 Prompt 设计器。
- **价值**：
  - 与 Qomo 当前认知最连续；
  - 最容易解释给现有用户；
  - 能最快把“模板 / 模块 / 变量”升级成更强的复用结构。
- **风险**：
  - 容易停留在“更高级的 Prompt 编辑器”；
  - 对 IDE 高价值场景的突破有限；
  - 工具、MCP、agent 装配会显得像附加项。
- **适用场景**：文档生成、需求分析、复盘、通用写作、轻量编码任务启动。

#### 方向 B：IDE 任务启动器 / Copilot Layer

- **定义**：把产品聚焦为 IDE 中的“任务启动层”，核心价值是从代码上下文一键调用预配置工作流。
- **价值**：
  - 直接打中高频用户最痛的时刻；
  - 能突出 Web 与插件的互补关系：Web 负责配置，IDE 负责调用；
  - 产品故事清晰，容易形成差异化。
- **风险**：
  - 插件优先会反向压缩 Web 端想象空间；
  - 可能让产品过于绑定编码场景；
  - 若 IDE 集成能力不强，体验会迅速失真。
- **适用场景**：编码任务启动、代码审查、调试排障、生成变更计划、测试补齐。

#### 方向 C：能力化 Prompt 工作台（平衡型）

- **定义**：把 Prompt、上下文、约束、工具、skills 统一抽象为“可装配能力”，形成可跨 Web / IDE 复用的 AI 工作单元。
- **价值**：
  - 最符合“带插槽的 Prompt 工作台”愿景；
  - 兼顾生成型与轻执行型；
  - 更容易成为 Qomo 2.x 的中心定义。
- **风险**：
  - 抽象层级更高，首次理解成本更高；
  - 如果对象模型不克制，会快速变复杂；
  - 容易在“提示生成”和“执行编排”之间摇摆。
- **适用场景**：跨 Web/IDE 的复用任务包、角色化工作流、个人最佳实践资产化。

#### 方向 D：Agent 装配台 / 轻量执行平台

- **定义**：把插槽直接扩展为 agent、工具与 MCP 的执行编排界面，Prompt 只是其中一个部件。
- **价值**：
  - 上限最高，战略想象空间最大；
  - 如果做好，会形成明显的平台化跃迁。
- **风险**：
  - 明显超出当前 Qomo 的自然复杂度；
  - 技术、安全、权限与调试成本陡增；
  - 很容易过早进入“全自动 Agent 平台”叙事。
- **适用场景**：复杂多步任务、工具链路固定的专业流程、实验型自动化工作流。

### 5. 第四轮发散：初版功能结构与对象模型草图

#### 5.1 一个较稳妥的核心判断

- 本产品的最小单位不应再只是“Prompt 文本”，而应是 **Work Unit（工作单元）**。
- 一个 Work Unit 可以理解为：
  - 一个基础 Prompt 骨架；
  - 若干有类型的 slots；
  - 一组可挂载的 capabilities；
  - 一套上下文与约束；
  - 一个明确的运行方式（仅生成 / 半执行 / 扩展执行）。

#### 5.2 可讨论的最小对象模型

- **Workbench Item / Work Unit**：用户真正保存与复用的主对象。
- **Prompt Skeleton**：基础提示骨架，定义核心任务意图。
- **Slot**：带类型的插槽，可承载变量、上下文、能力或规则。
- **Capability**：可装入 slot 的能力单元，例如 skill、tool binding、MCP connector、agent role、context provider。
- **Context Block**：代码片段、文档摘要、知识背景、文件选择等上下文片段。
- **Guardrail Block**：边界、输出格式、自检清单、禁止项、风险提示。
- **Runtime Instance**：一次实际执行时的绑定结果，区分于设计时资产。

#### 5.3 Slot 不应只是占位符

- 更合理的定义是：**slot 是一种能力接口**。
- 它至少应包含：
  - 类型（文本 / 上下文 / 工具 / agent / 规则）；
  - 是否必填；
  - 默认值或默认挂载；
  - 可选范围；
  - 执行时机；
  - 权限提示或风险等级。

#### 5.4 三种运行深度需要被分层看待

- **生成型**：输出最终 Prompt，交给外部 AI 使用。
- **辅助执行型**：除了生成 Prompt，还帮用户注入上下文、选择文件、填充变量。
- **编排执行型**：进一步触发工具、MCP、子 agent 或多阶段任务流。

一个重要结论是：

- **Qomo 的未来演进未必需要一步跨到“编排执行型”**；更现实的路径，是先把生成型与辅助执行型做扎实，再决定是否进入执行编排。

### 6. 第五轮发散：Web + VS Code 技术与插件边界判断

#### 6.1 双端共享什么，双端分开什么

- **应该共享**：
  - 领域模型；
  - 资产配置协议；
  - slot / capability 的约束与校验逻辑；
  - 基础渲染与预览规则；
  - 导入导出格式。
- **应该分开**：
  - IDE 上下文采集；
  - 编辑器命令与交互；
  - 文件选择、代码范围绑定、工作区权限；
  - Web 端的管理视图、资产整理、可视化设计体验。

#### 6.2 插件环境的关键边界

- 不是所有 capability 都应默认允许在插件内执行。
- 至少需要区分三层：
  - **安全静态层**：纯 Prompt / 约束 / 模板填充；
  - **受控上下文层**：读取当前文件、选中文本、工作区文件树；
  - **扩展执行层**：工具调用、MCP、子 agent、可能改写工作区的动作。
- 这意味着产品定义会直接受权限模型影响：
  - 如果权限边界做不清，执行型方案会严重受阻；
  - 如果边界清晰，平衡型方案有较大落地空间。

#### 6.3 同步策略判断

- **导入导出优先**：最轻，适合早期验证，但体验割裂。
- **本地优先 + 可选同步**：更适合插件场景，也更符合“IDE 高频复用”的稳定性要求。
- **云端优先**：管理体验最好，但会更早引入账号、冲突、离线与隐私问题。

初步判断：

- 如果以未来演进为前提，**本地优先 + 结构化资产文件 + 后续可选云同步** 是较稳妥的中间路线。

### 7. 第六轮发散：Qomo 重构路线选项

#### 路线 1：在现有 Qomo 上渐进升级

- **思路**：从模板、模块、变量出发，逐步引入 typed slots、context blocks、guardrails，再延展到 capability。
- **优点**：连续性最好，用户心智迁移成本最低。
- **风险**：旧模型包袱较重，容易把新产品做成“旧结构上的补丁”。

#### 路线 2：Qomo 1.x / 2.x 双轨过渡

- **思路**：保留当前 Qomo 作为 Prompt 资产层，同时并行孵化“能力化 Prompt 工作台”。
- **优点**：探索空间更大，不必被旧边界绑死。
- **风险**：品牌叙事与产品资源会被分散，用户可能困惑“两个 Qomo 的关系”。

#### 路线 3：先抽核心引擎，再回接双端产品

- **思路**：先定义新的共享对象模型与配置核心，再让 Web 与 VS Code 共用这套内核。
- **优点**：从一开始就为双端一致性与长期演进打底。
- **风险**：短期看起来更慢，也更容易脱离用户场景。

#### 初步倾向

- 最值得进一步验证的，不是“纯渐进”也不是“直接重建全平台”，而是：
  - **产品上走 Qomo 1.x → Qomo 2.x 的过渡带；**
  - **架构上优先抽共享核心模型；**
  - **体验上先聚焦生成型 + 辅助执行型。**

这条路线兼顾了连续性、双端复用与风险控制。

### 8. 适度收敛：4 个候选方向的横向判断

#### 候选方向对比摘要

- **A. 结构化 Prompt 资产工作台**
  - 价值：最稳、最连续、最容易承接现有 Qomo。
  - 风险：容易创新不足，难以形成 IDE 侧强差异化。
  - 适用：若当前目标是低风险演进与资产模型升级。

- **B. IDE 任务启动器 / Copilot Layer**
  - 价值：最贴近高频刚需，最容易打到“减少重复交代”的核心痛点。
  - 风险：可能把产品过度收缩到插件能力，不利于长期平台化。
  - 适用：若要优先验证 IDE 高频场景的产品抓力。

- **C. 能力化 Prompt 工作台（平衡型）**
  - 价值：最符合本轮问题定义，也最可能成为 Qomo 的未来主线。
  - 风险：抽象复杂度更高，需严控对象模型边界。
  - 适用：若要同时保住 Web 的资产能力与 IDE 的高频复用价值。

- **D. Agent 装配台 / 轻量执行平台**
  - 价值：天花板最高，战略延展性最强。
  - 风险：最容易超范围，也最容易过早陷入实现与权限复杂度。
  - 适用：更像中远期探索方向，而非当前最优先切入点。

#### 当前更建议继续推进的方向

- **首选探索主线：方向 C（能力化 Prompt 工作台）**
- **建议配套验证视角：方向 B（IDE 任务启动器）**

理由是：

- C 最符合“Web + VS Code + 插槽化能力复用”的总体愿景；
- B 能帮助我们保持场景抓手，避免 C 变成抽象概念工程；
- A 可作为过渡兼容层保留；
- D 暂作为远期参考，而非本轮决策目标。

### 9. 待验证假设与关键分歧

#### 待验证假设

- 用户真正想复用的是“任务工作单元”，而不是“Prompt 文本增强版”。
- Web 负责设计、插件负责调用的双端分工，对用户是自然的而非割裂的。
- 插槽化对象模型可以被普通高频用户理解，不会只适合高级玩家。
- 生成型 + 辅助执行型，就足以形成显著价值，不必一开始做重编排。

#### 关键分歧

- 产品对外应该先讲“Prompt 工作台”，还是先讲“IDE 任务启动器”。
- slot 到底是“增强型变量”，还是“能力接口”。
- capability 是否在早期就包含可执行工具，还是先只作为可配置绑定。
- Qomo 2.x 应该被定义为重构升级，还是作为并行新形态探索。

### 10. 建议下一步进入的 BMAD 流程

#### 推荐路径

1. **先进入 `quick-spec`**
   - 目标：把方向 B 与方向 C 的分歧进一步压实。
   - 建议聚焦：
     - 目标用户是谁；
     - 首批高价值场景是哪 2-3 个；
     - 产品首页级对象到底是模板、任务包、还是 work unit；
     - Web 与 VS Code 各自的一号任务是什么。

2. **再进入 `create-product-brief`（面向未来演进分支）**
   - 前提：若 quick-spec 后仍认为方向 C 是主线。
   - 产物建议：形成一份明确区别于现有基线的“Qomo 2.x / Prompt Workbench”产品简报。

3. **暂不进入架构细化或实现工作流**
   - 在对象模型、产品边界、插件角色未收敛前，不建议直接推进技术设计或原型实现。

#### 一句话建议

- **下一步最合理的 BMAD 动作，不是立刻做实现，而是用 `quick-spec` 把“能力化 Prompt 工作台”与“IDE 任务启动器”之间的主次关系定清。**

## 附录：quick-spec 输入整理与关键分歧（2026-03-06）

> 用途：作为下一波 `/bmad-bmm-quick-spec` 的统一输入材料，优先服务于 `quick-spec` Step 1 的问题定义与范围确认。

### 1. quick-spec 的统一问题陈述

如果 Qomo 要从 **1.x 的 Prompt 资产工作台**，演进为一个**可跨 Web 与 VS Code 复用的能力化 Prompt 工作台**，那么下一步需要先收敛的，不是完整执行平台细节，而是：

- **产品主线**到底应以方向 C（能力化 Prompt 工作台）为核心，还是以方向 B（IDE 任务启动器 / Copilot Layer）为核心；
- **首批目标用户**到底是谁，避免继续用“泛 Prompt 用户”做过宽定义；
- **首批最值得支持的 2-3 个高价值场景**是什么，确保产品不是抽象概念工程；
- **最小对象模型边界**应该收敛到哪一层，既能承接 Qomo 1.x 资产，又不提前掉进重编排复杂度；
- **Web 与 VS Code 的一号任务**分别是什么，确保双端分工清晰而非重复建设；
- **Qomo 1.x → 2.x 的过渡表述**如何成立，既保留连续性，又不掩盖产品升级。

一句话版本：

- **本轮 quick-spec 要解决的，是“Qomo 2.x 先以什么主线、服务谁、解决哪几个高频任务、用什么最小对象模型落地”，而不是现在就定义完整 Agent 执行平台。**

### 2. 建议作为 quick-spec 起点的预设前提

以下内容建议作为下一波 quick-spec 的**默认起始假设**，除非在讨论中出现强反证：

- **主线暂定：C 为主，B 为验证视角。**
  - 即：产品定义以“能力化 Prompt 工作台（平衡型）”为主；
  - 但首批价值验证与落地抓手，以“IDE 任务启动器 / Copilot Layer”视角来约束抽象度。
- **首批用户暂定：高频使用外部 AI 辅助编码的开发者 / 技术负责人 / AI-native builder。**
  - 个人使用优先；
  - 暂不把团队协作与权限系统作为首批成立条件。
- **首批场景暂定：编码任务启动、代码审查/变更评估、调试排障/修复计划。**
- **对象模型暂定：以 Work Unit 为顶层保存对象。**
  - `Template / Module / Constraint Pack / Variable` 不直接废弃，而是作为向 2.x 对象模型映射的来源。
- **能力边界暂定：先做生成型 + 辅助执行型，不做完整编排执行平台。**

### 3. 必须收敛的关键分歧清单

#### 分歧 1：方向 C 与方向 B 的关系到底是什么

- **待决策问题**：
  - 方向 C 是产品主定义，方向 B 只是首批场景透镜；
  - 还是方向 B 才是主产品，方向 C 只是底层抽象。
- **当前建议倾向**：
  - **C 做产品主线，B 做验证视角与首批落地入口。**
- **判断标准**：
  - 是否能同时解释 **Web 的资产设计价值** 与 **IDE 的高频调用价值**；
  - 是否避免把产品过早收缩成“只在插件里成立的功能集合”；
  - 是否能在不进入复杂执行编排的前提下，仍形成清晰差异化；
  - 是否能承接现有 Qomo 1.x 的模板/模块/约束包基线。

#### 分歧 2：首批目标用户到底是谁

- **待决策问题**：
  - 是继续面向“高频 Prompt 用户”的宽口径；
  - 还是先收紧到“高频 AI 编码工作流用户”。
- **当前建议倾向**：
  - **先收敛为：高频在 VS Code + 外部 AI 之间切换的开发者与技术负责人。**
- **判断标准**：
  - 这类用户是否存在足够高频、可重复的“任务启动前重复交代”痛点；
  - 这类用户是否天然需要 **Web 端策划/沉淀** 与 **IDE 端调用/执行** 的双端配合；
  - 产品是否可以在**不先做协作权限系统**的前提下对其成立；
  - 用户心智是否更容易理解“工作单元复用”而不是“高级 Prompt 编辑器”。

#### 分歧 3：首批最值得优先支持的 2-3 个高价值场景是什么

- **当前建议倾向**：
  1. **编码任务启动 / Dev Brief**
     - 从需求、issue、代码上下文出发，快速生成“澄清问题 + 执行计划”的工作单元。
  2. **代码审查 / 变更评估**
     - 面向 diff / PR / 变更说明，复用审查视角、输出结构与风险边界。
  3. **调试排障 / 修复计划（可包含测试补齐）**
     - 面向报错、日志、上下文与修复边界，生成排障/修复/验证计划。
- **判断标准**：
  - 场景是否足够高频，且“重复交代成本”显著；
  - 场景是否能被同一套 `Work Unit + Slot + Capability` 模型支撑；
  - 场景是否天然适合 **Web 配置、VS Code 调用** 的双端分工；
  - 场景是否在“生成型 + 辅助执行型”阶段就能交付清晰价值。

#### 分歧 4：最小对象模型边界收敛到哪里

- **当前建议倾向**：
  - 顶层保存对象先收敛为 **Work Unit**；
  - `Slot` 定义为**带类型的能力接口**，而不是增强型变量；
  - `Capability` 先定义为**可配置、可挂载、可复用的能力单元**；
  - `Context Block` 与 `Guardrail Block` 在 quick-spec 阶段可视为 `Capability` 的具体类型或 `Slot` 的标准化载荷；
  - **不建议**在本轮把 `Agent / Skill / MCP / Tool / Context Provider` 全部拉成平级顶层对象。
- **判断标准**：
  - 是否足够小，普通目标用户也能理解；
  - 是否能从 Qomo 1.x 的 `Template / Module / Constraint Pack / Variable` 顺滑映射过来；
  - 是否能被 Web 与 VS Code 共用，而不严重依赖宿主能力；
  - 是否为未来扩展到更强执行能力留出空间，但不强迫本轮先解决权限与编排问题。

#### 分歧 5：Web 与 VS Code 各自的一号任务是什么

- **当前建议倾向**：
  - **Web 一号任务**：设计、配置、预览、整理与复用 `Work Unit`。
  - **VS Code 一号任务**：在当前工作区上下文中，快速启动一个现成 `Work Unit`，补齐必要上下文后交付给外部 AI / Copilot Layer 使用。
- **判断标准**：
  - 是否符合各自宿主环境的天然优势；
  - 是否能显著减少“双端都在做同一件事”的重复建设；
  - 是否在不引入复杂权限模型前，就能形成可感知价值；
  - 是否能让用户直观理解：**Web 是设计台，VS Code 是启动台。**

#### 分歧 6：`Qomo 1.x → 2.x` 应如何表述

- **当前建议倾向**：
  - **Qomo 1.x**：Prompt 资产层，解决“把 Prompt 管起来”；
  - **Qomo 2.x**：能力化 Prompt 工作台，解决“把 AI 工作方式复用起来”；
  - 1.x 不是被推翻，而是成为 2.x 的**兼容层、迁移来源与认知过渡带**。
- **建议映射关系**：
  - `Template → Work Unit Skeleton`
  - `Module / Constraint Pack → Capability / Guardrail Preset`
  - `Variable → Typed Slot`
- **判断标准**：
  - 是否保留了用户与已有文档的连续性；
  - 是否避免把 2.x 讲成“完全另一个产品”而造成断裂；
  - 是否能清晰解释迁移路径与边界；
  - 是否不会过度承诺“已经是完整执行平台”。

### 4. 可直接沿用的脑暴结论

以下内容已经在上一轮脑暴中相对收敛，可直接进入 quick-spec：

- **主线优先级**：方向 C（能力化 Prompt 工作台）优先继续推进；方向 B（IDE 任务启动器）作为关键验证视角。
- **最小保存对象倾向**：未来的最小单位不应再只是 Prompt 文本，而应是 **Work Unit**。
- **slot 的定义倾向**：slot 更像**能力接口**，不只是占位符。
- **产品能力边界倾向**：先做 **生成型 + 辅助执行型**，不直接跳到完整编排执行平台。
- **双端边界倾向**：
  - 共享：领域模型、资产协议、slot/capability 校验逻辑、预览与导入导出格式；
  - 分开：IDE 上下文采集、编辑器命令、文件选择、工作区权限、Web 管理视图。
- **重构路线倾向**：
  - 产品叙事上走 `Qomo 1.x → 2.x` 的过渡带；
  - 架构上优先抽共享核心模型；
  - 体验上先聚焦生成与轻执行。
- **方向 A / D 的位置**：
  - A（结构化 Prompt 资产工作台）可作为兼容层与过渡层保留；
  - D（Agent 装配台 / 轻量执行平台）暂作中远期参考，不进入本轮 quick-spec 核心决策。

### 5. 本轮明确不做的事情

- **不定义完整 Agent / MCP / Tool 执行编排协议。**
- **不决定所有 capability 类型、权限模型与宿主 API 细节。**
- **不把讨论扩展到所有 IDE / 所有宿主平台。** 当前只以 VS Code 作为插件验证对象。
- **不直接进入架构细化、原型实现或技术 Spike。**
- **不在本轮锁定团队协作、权限系统、社区生态、商业化与定价。**
- **不把 Qomo 2.x 直接表述成“全自动 Agent 平台”。**
- **不推翻当前 Qomo 1.x 的 PRD / UX / Architecture 基线。** 本轮是面向未来演进分支的收敛输入，而不是替换现有交付基线。

### 6. 建议下一波正式 quick-spec 的推进顺序

结合 `/bmad-bmm-quick-spec` 的 Step 1“先确认问题、范围与解法 delta”的要求，建议按以下顺序推进：

1. **先确认统一问题陈述与工作标题**
   - 先回答“这次 quick-spec 到底在定义什么产品增量”，避免一开始就陷入对象模型枝节。
2. **先压实方向 C 与方向 B 的主次关系**
   - 先定“主产品定义”与“首批验证视角”，避免双核心叙事。
3. **再锁定首批目标用户与 2-3 个高价值场景**
   - 没有用户与场景，后续对象模型判断会失真。
4. **再收敛最小对象模型边界**
   - 优先冻结 `Work Unit / Slot / Capability` 的最小解释，再讨论其余概念是否作为类型或扩展层。
5. **再明确 Web 与 VS Code 的一号任务与宿主分工**
   - 让产品结构与平台边界一起成立，而不是事后拼接。
6. **最后统一 `Qomo 1.x → 2.x` 的过渡表述**
   - 把对象映射、兼容关系与阶段性边界讲清楚，作为后续 product brief / architecture 的输入。

### 7. 建议带入 quick-spec 的一句话默认结论

- **建议把下一波 quick-spec 的默认起点设为：Qomo 2.x 以“能力化 Prompt 工作台”为主线定义，以“IDE 任务启动器”作为首批验证视角，首批服务高频 AI 编码工作流用户，围绕 Work Unit / Slot / Capability 的最小对象模型，先解决任务启动、代码审查、调试排障三类高价值场景。**

## 附录：quick-spec 结果（2026-03-06）

> 性质说明：本结果属于 **Qomo 的未来演进探索**，用于收敛下一阶段产品定义，不替代当前已经存在的 PRD / UX / Architecture / MVP 基线。

### 1. quick-spec 的核心问题陈述

本轮 quick-spec 要解决的，不是“Qomo 要不要直接变成完整 Agent 执行平台”，而是：

- 在保持 Qomo 1.x 连续性的前提下，**Qomo 2.x 应该先以什么主线定义自己**；
- **首批最值得服务的用户是谁**，避免继续停留在“泛 Prompt 用户”的宽口径；
- **首批最值得优先支持的 2-3 个高价值场景是什么**，确保未来演进有可落地的任务抓手；
- **最小对象模型边界**应先收敛到哪里，既能承接 1.x 资产，又不提前掉进复杂执行编排；
- **Web 与 VS Code 各自的一号任务**如何分工，避免双端叙事互相打架；
- **`Qomo 1.x → 2.x` 应如何表述**，既保留连续性，又清楚说明升级点。

一句话总结：

- **本轮要收敛的是“Qomo 2.x 先以什么产品主线、服务谁、解决哪几个高频任务、用什么最小对象模型成立”，而不是现在就定义完整执行平台。**

### 2. 已收敛的关键决策

#### 决策 1：方向 C 与方向 B 的关系

- **结论：方向 C 为主线，方向 B 为验证视角。**
- 也就是说：
  - 对外产品定义以 **能力化 Prompt 工作台（平衡型）** 为核心；
  - 首批价值验证与落地抓手，以 **IDE 任务启动器 / Copilot Layer** 视角来约束抽象度。
- 这样处理的原因是：
  - 方向 C 更能同时解释 **Web 端的资产设计价值** 与 **VS Code 端的高频调用价值**；
  - 方向 B 能帮助产品保持场景抓手，避免方向 C 变成抽象概念工程；
  - 这也更有利于保留 Qomo 1.x 的连续性，而不是把产品过早收缩成“一个插件功能集合”。

#### 决策 2：首批目标用户

- **结论：首批目标用户收敛为高频 AI 编码工作流用户。**
- 更具体地说，优先服务：
  - 高频在 **VS Code 与外部 AI / Copilot Layer** 之间切换的开发者；
  - 需要反复发起编码任务、审查任务、排障任务的技术负责人 / AI-native builder。
- 本轮不把以下人群作为首批成立条件：
  - 泛内容创作型 Prompt 用户；
  - 必须依赖团队协作权限系统的组织型用户。

#### 决策 3：首批最值得优先支持的高价值场景

- **结论：优先支持以下 3 类场景。**

1. **编码任务启动 / Dev Brief**
   - 把需求、issue、代码上下文与约束整理成可复用的任务启动单元。
2. **代码审查 / 变更评估**
   - 面向 diff / PR / 变更说明，复用审查视角、风险边界与输出结构。
3. **调试排障 / 修复计划**
   - 面向报错、日志、相关文件与修复范围，生成排障路径、修复方案与验证计划。

- 这 3 个场景被优先选中的原因：
  - 高频；
  - 重复交代成本高；
  - 都可以被同一套 `Work Unit + Slot + Capability` 最小模型支撑；
  - 在“生成型 + 辅助执行型”阶段就能交付明确价值。

#### 决策 4：最小对象模型边界

- **结论：本轮最小对象模型收敛为 `Work Unit / Slot / Capability`。**
- 当前建议解释为：
  - **Work Unit**：用户真正保存、复用、启动的主对象；它代表一个任务工作单元，而不只是 Prompt 文本。
  - **Slot**：带类型的能力接口，而不是单纯变量占位；可以承载上下文、规则、输入、可挂载能力等。
  - **Capability**：可配置、可挂载、可复用的能力单元；在本轮可以涵盖 context/guardrail/preset 等能力块。
- 本轮明确**不做**：
  - 不把 `Agent / Skill / MCP / Tool / Context Provider` 全部拉成平级顶层对象；
  - 不定义完整运行时协议、权限系统与执行编排模型。

#### 决策 5：Web 与 VS Code 的一号任务

- **结论：Web 是设计台，VS Code 是启动台。**
- 具体收敛为：
  - **Web 一号任务**：设计、配置、预览、整理与复用 `Work Unit`。
  - **VS Code 一号任务**：在当前工作区上下文中快速启动一个现成 `Work Unit`，补齐必要上下文后交付给外部 AI / Copilot Layer 使用。
- 这样划分的价值在于：
  - 让双端的宿主优势自然分工；
  - 避免“双端都在做同一件事”的重复建设；
  - 让用户更容易理解：**Web 负责策划与资产化，VS Code 负责贴近任务现场地启动与调用。**

#### 决策 6：`Qomo 1.x → 2.x` 的过渡表述

- **结论：Qomo 1.x 不是被推翻，而是成为 Qomo 2.x 的兼容层、迁移来源与认知过渡带。**
- 推荐表述：
  - **Qomo 1.x**：Prompt 资产层，解决“把 Prompt 管起来”；
  - **Qomo 2.x**：能力化 Prompt 工作台，解决“把 AI 工作方式复用起来”。
- 建议映射关系：
  - `Template → Work Unit Skeleton`
  - `Module / Constraint Pack → Capability / Guardrail Preset`
  - `Variable → Typed Slot`
- 这意味着：
  - 2.x 是升级与扩展，而不是“完全另一个产品”；
  - 但也不能把 2.x 描述成“1.x 的小修小补”，因为保存对象、复用粒度与双端结构已经发生跃迁。

### 3. 默认继承且继续有效的约束

除非后续有强反证，本轮 quick-spec 继续继承以下约束：

- **不直连模型**
- **个人使用优先**
- **不做团队协作权限系统**
- **先以“生成型 + 辅助执行型”为主**

这些约束的意义是：帮助 2.x 在早期保持产品边界清晰，先验证“工作单元复用”是否成立，而不是过早进入平台化复杂度。

### 4. 仍待验证的少量问题

本轮不再保留大量开放分歧，只留下以下少量验证问题：

1. **首批用户是否需要进一步从“高频 AI 编码工作流用户”收窄到更具体的人群切片**
   - 例如：独立开发者、技术负责人、AI-native builder，哪个最适合作为对外第一叙事。
2. **`Slot` 的用户心智是否足够自然**
   - 需要确认目标用户更容易理解“带类型的能力接口”，还是需要一个更易传播的产品语言。
3. **VS Code 端首批启动体验的最小闭环是什么**
   - 需要进一步明确第一版是“任务启动 + Prompt 交付”，还是要带少量辅助执行动作，才能形成足够明显的价值感。

### 5. 建议下一步进入的 BMAD 流程

- **建议下一步进入 `create-product-brief`。**
- 原因是：
  - 本轮 quick-spec 已经完成主线、用户、场景、对象模型边界与双端分工的第一轮收敛；
  - 剩余问题已被压缩为少量验证项，不再构成继续做一轮完整 quick-spec 的必要前提；
  - 进入 `create-product-brief` 更适合把这些决策转写为更正式的未来演进 brief，供后续 PRD/UX/Architecture 分支继续展开。

建议带入下一步 brief 的一句话定义：

- **Qomo 2.x 是一个面向高频 AI 编码工作流用户的能力化 Prompt 工作台：Web 负责设计与管理可复用的 Work Unit，VS Code 负责在任务现场快速启动它们；产品先以生成型 + 辅助执行型为主，通过 `Work Unit / Slot / Capability` 的最小对象模型，把“复用 Prompt”升级为“复用 AI 工作方式”。**

### 6. 对正式 workflow 的提醒：哪些节点需要停下让用户决策

5. **Step 4 - Metrics**
   - 成功指标与 KPI 草稿确认后，必须停在 **A/P/C**。
6. **Step 5 - Scope**
   - MVP scope、非目标、未来愿景草稿确认后，必须停在 **A/P/C**。
7. **Step 6 - Complete**
   - 完成后需要让用户决定：是复盘 brief、进入下一工作流，还是发起 revision；不能默认替用户跳到后续 workflow。
